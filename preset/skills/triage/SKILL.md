# Triage

> **Repo version first:** if this repository has `.agents/skills/triage/SKILL.md`, follow that file instead of this one. It's tailored to the repository.

Move issues on the project's issue tracker through a small state machine of triage roles. The outcome for most issues is an **agent brief**: the contract an unattended agent later builds from with the `implement` skill.

If the repo treats external pull requests as a request surface (the tracker guide says so), triage covers them too: **a PR is an issue with attached code**, with the same roles and states and a few differences marked "for a PR" below. Resolve a bare `#42` to an issue or a PR as the tracker guide describes.

Every comment or issue you post during triage **must** start with this line:

```
> *This was generated by AI during triage.*
```

The issue tracker and triage label vocabulary are in `.agents/issue-tracker.md`. If that file doesn't exist, generate it first with the issue-tracker recipe: `.agents/references/issue-tracker.md` in the project, else `~/.agents/references/issue-tracker.md`.

## Roles

Two **category** roles: `bug` (something is broken) and `enhancement` (a new feature or improvement).

Five **state** roles:

- `needs-triage`: a maintainer needs to evaluate it
- `needs-info`: waiting on the reporter
- `ready-for-agent`: fully specified, ready for an unattended agent
- `ready-for-human`: needs a human to implement it
- `wontfix`: won't be actioned

For a PR, the states read against the attached code: `ready-for-agent` means a brief is attached and an agent takes the next step on the diff; `ready-for-human` means it's ready for a human to merge.

These are role names. The tracker guide maps them to the real labels. If a role has no label there, ask the maintainer which label to use and add the mapping to `.agents/issue-tracker.md`.

Every triaged issue carries exactly one category and one state. If states conflict, flag it and ask the maintainer before doing anything else.

**Transitions:** an unlabeled issue normally goes to `needs-triage` first. From there it moves to `needs-info`, `ready-for-agent`, `ready-for-human` or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time; flag transitions that look unusual and ask before proceeding.

## Invocation

The maintainer describes what they want in plain words. Interpret it and act, for example: "show me anything that needs my attention", "let's look at #42", "move #42 to ready-for-agent", "what's ready for agents to pick up?".

When the maintainer delegates ("I'm away", "decide for me"), every point below that waits for direction takes your recommended option instead: record it as a decision in the brief or comment and continue. That covers follow-up issues too: file each one and triage it in the same run.

## Show what needs attention

Query the tracker and present three buckets, oldest first:

1. **Unlabeled:** no triage role.
2. **`needs-triage`:** evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes:** needs another look.

When PRs are in scope, include external PRs and tag each line `[PR]` or `[issue]`. Discovery shows only external PRs (the tracker guide defines who counts as external); an explicitly named PR is always triaged, whoever wrote it.

Leave out issues that other skills produced already triaged: specs from `to-spec`, tickets from `to-tickets` (a `## What to build` section), and anything labelled `wayfinder:*`.

Show counts and a one-line summary per item. Let the maintainer pick.

## Triage one issue or PR

1. **Gather context.** Read `.agents/issue-tracker.md` first, in its own step. Then read the full issue or PR (body, comments, labels, author, dates; for a PR, the diff too) with the read operations it names. Don't build a read command from memory: flag combinations that look right can fail. Parse any prior triage notes so you don't re-ask settled questions. Explore the codebase using the project's glossary, respecting the ADRs in the area. In a subagent that returns only what it found and where it looked, run two checks:
   - **Redundancy:** search for an existing implementation of the requested behavior by domain concept, not just the request's wording. If found, it's an already-implemented `wontfix` (step 5).
   - **Prior rejection:** follow the out-of-scope concept (`.agents/concepts/out-of-scope/CONCEPT.md`, or under `~/.agents/`): read `.out-of-scope/` and surface any record that matches by concept.
2. **Recommend.** Give the maintainer your category and state with reasoning, and a short summary of the relevant code, including whether it's already implemented. Wait for direction.
3. **Verify the claim** before any grilling. For a bug, reproduce it from the reporter's steps. For a PR, check it out and run the relevant tests or commands to confirm the diff does what it claims. Report the outcome: confirmed (with the code path), failed, or not enough detail (a strong `needs-info` signal). When verification disproves something in the body, correct it where later readers look first: edit the body when the maintainer or an agent wrote it, otherwise open the brief with the correction.
4. **Grill, if needed.** If the request needs fleshing out, use the `grilling` and `domain-modeling` skills together: grill it into shape a round of questions at a time, updating `GLOSSARY.md` and ADRs as decisions land.
5. **Apply the outcome.**
   - `ready-for-agent`: agree with the maintainer on the seams the tests go through, then post an agent brief that records them. Read [references/agent-brief.md](references/agent-brief.md) first.
   - `ready-for-human`: the same structure as an agent brief, plus why it can't be delegated (judgment calls, external access, design decisions, manual testing).
   - `needs-info`: post triage notes ([references/needs-info.md](references/needs-info.md)).
   - `wontfix`, with the comment depending on why:
     - **Already implemented:** point to where it lives, then close. Don't write to `.out-of-scope/`.
     - **Rejected bug:** a polite explanation, then close.
     - **Rejected enhancement:** record it as the out-of-scope concept describes, link the record in a comment, then close.
   - `needs-triage`: apply the role, with an optional comment on partial progress.

## Quick state override

If the maintainer says "move #42 to ready-for-agent", trust them and apply the role. Confirm what you're about to do (role changes, comment, close), then act. Skip grilling. Moving to `ready-for-agent` still needs an agent brief: ask the maintainer for the seams it records, then write it.

## Resuming

If prior triage notes exist, read them, check whether the reporter answered the open questions, and present an updated picture before continuing. Don't re-ask settled questions.
